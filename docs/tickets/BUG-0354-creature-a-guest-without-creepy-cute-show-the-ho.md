## Report
The owner's decision after BUG-0341 (2026-10-31, for 0.7.3.2): a guest whose game has the Creepy &
Cute parts pack sees the host's creatures unchanged; a guest without it no longer gets "cannot load
<host>'s world" but plays, the pack's parts shown as similar base game parts of the same kind (eye for
eye, mouth for mouth, ...; similar abilities). Never send the pack's files between players.

## Root cause
Not a bug: BUG-0341 refused such creatures and worlds (a game without the pack faults at 0x441F3B in
the model bake). What made substitution possible (observed, docs/re/creations.md#creations-part-substitutes):
the guest's game builds the host's creatures only from the records co-op registers (the world holds no
creation records), the model names each part by its id in place (`60 62 40` + 4 bytes, 0xFE written
`FE 00`), and the part props give each part's role (`0xB00F0FXX`: eye 0x0FE9, mouth 0x0FEC, grasper 0x0FE2,
foot 0x0FEF, none for details) and ability levels (`0x??C3E5XX`).

## Fix
`coop.fix creations.part_substitute` (creations.cpp `substitute_parts`, on a game without the pack only):
the ids of pack parts in this game's copy of a creature's model records are rewritten to the base part of
`kCreepyCuteSubstitutes` (content_packs.h, 119 entries generated by tools/part_substitutes.py from the
game's part props: the same role, the nearest abilities, the same cost and ranks, an id with as many 0xFE
bytes, so it fits in place) before the records are registered: a player's creature, a species of the host's
world, the host's own creation of its world. A part without a substitute, or whose substitute the game
lacks, keeps BUG-0341's refusal (`creations.missing_parts`). Log line per creature and a one-time notice
("Some Creepy & Cute parts are shown as similar base game parts ..."). `coop.creations parts <key>` (tests)
prints the parts of the model the game reads, how many are pack parts, and whether the species is built.
